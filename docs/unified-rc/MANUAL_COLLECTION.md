# Ручной сбор: оператор и настройка установки

OPERATOR-CONFIRMED: простой запуск, диапазон скорости и количество карточек;
дополнительные настройки сохранить. REPOSITORY-VERIFIED: это интерфейс над
существующими queue/worker/receipts, без второго сборщика и изменений схемы.

## Для оператора

1. Поставщики → источник. Основные поля: пауза «от–до», количество карточек.
2. Если меняете скорость, сохраните диапазон. Это не запускает сбор и не меняет
   настройки уже созданных заданий. Указанная пауза — между началами запросов;
   параллельность и ограничения сайта также влияют на итоговую скорость.
3. На той же странице видны отдельные причины недоступности: источник выключен,
   профиль не подтверждён или не разрешён исполнителю, исполнитель выключен.
   Администратор может включить источник и подтвердить сохранённую скорость
   прямо здесь; эти действия сами по себе не запускают задания.
4. Для подготовленной установки: количество → «Подготовить запуск» → проверить
   выбранные карточки/скорость → «Подтвердить запуск». Статус — в «Сбор и запуски».
   Создаётся одно штатное задание. Результат сохранения проверяется отдельно.

Поиск новых товаров находится в дополнительном разделе. Все прежние настройки
тайм-аутов, попыток, расписания, TTL и XML сохранены на странице настроек.
Экспорт в сайт не включается ни одной из этих форм.

## Почему HOST_PROFILE_DIGEST_NOT_APPROVED не лечится повторным нажатием

REPOSITORY-VERIFIED: approve_parsing_host сохраняет подтверждение администратора
в suppliers.crawl_settings.host_policy_approval. compile_policy дополнительно
проверяет точное разрешение в STERBRUST_APPROVED_HOST_POLICIES процесса исполнения.
Это две разные проверки. Ранее страница имитировала вторую проверку первой и
могла скрывать причину будущего отказа. Теперь UI не объявляет такой профиль готовым.

Администратор установки должен однократно проверить и согласовать:

- точные роли, адрес БД и SQL identity этой установки; существующие RC pin не сняты;
- штатную очередь и работающий worker;
- отдельные разрешения source runtime, supplier HTTP и source writes;
- точный утверждённый профиль для каждого выбранного host/source. Использовать
  текущий SHA со страницы настроек и тот же профиль в web/worker; при объединении
  карты STERBRUST_APPROVED_HOST_POLICIES сохранять остальные host и namespaces;
- новый допустимый LIVE-контракт/окно/состав URL там, где их требует текущий запуск.

Обновление кода и изменение профиля не разрешают автоматически менять эти
настройки на реальном сервере. Не ставить произвольный digest и не снимать
проверку compile_policy. После изменения скорости старое разрешение может
не совпадать. Изменение количества при прежней скорости не меняет сам host-профиль,
но меняет подтверждаемую партию и её immutable snapshot.

## Приёмка после установки разработчиком

До LIVE, только чтение/фикстуры: проверить новый экран, возврат с ошибки, роль
ADMIN/OPERATOR/VIEWER, недоступность записи в read-only, неизменность прочих
настроек при быстром сохранении. В сохранённом профиле не должно быть float-хвостов
в отображении; исходные значения БД при отображении не переписываются.

Затем отдельно согласовать один ограниченный сбор. Сверить фактические запросы,
предел карточек/скорость/STOP, receipts, сохранение в PostgreSQL и старые связи.
Это не разрешение на массовый сбор, повтор consumed-контракта, matching apply,
52 предложения Векпром, расписание, импорт или deployment.

DONE: код UI и диагностическая правка; APPLIED: feature checkout.
VERIFIED: offline regression и изолированный браузер, не целевой сервер.
Основная БД, рабочие данные, Content Studio и история XML этим этапом не изменялись.
