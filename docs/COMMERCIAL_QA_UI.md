# Единая локальная панель Universal Supplier (QA)

Эта инструкция запускает **существующую FastAPI операторскую панель** в
специальном локальном режиме. Она не использует Docker, не запускает миграции, scheduler, orchestrator,
matching, selection или ESOL.

Публичный HTTP-сбор начинается только после явного нажатия оператора.
По умолчанию включена проверка без записи. Старый ограниченный режим до трёх
карточек сохранён как тестовый; полный режим использует закреплённый sitemap
manifest трёх источников и 20-секундную паузу между любыми GET. QA write
появляется только с двумя write-флагами, доступной и прошедшей preflight
Stage 4 QA-базой и отдельным подтверждением в форме. Рабочую БД он не меняет.

## Обычный операторский запуск

Из обычного пользовательского PowerShell в корне репозитория используйте один launcher:

```powershell
.\scripts\start_commercial_qa_ui.ps1
```

Эта команда лишь проверяет уже работающие базы. Если их нужно штатно поднять
из **обычного пользовательского PowerShell**, оператор может явно выбрать
`-StartLocalDatabases`. Launcher сначала проверяет PG_VERSION, system identifier,
порт, SQL identity и соответствие `postmaster.pid` известному data directory;
чужой listener или несоответствие останавливают запуск. PostgreSQL из
ограниченного контекста Codex не запускают. Для QA-записи добавьте
`-EnableQaWrite`; без него панель остаётся read-only и dry-run.

Если локальная QA-панель уже запущена и нужно применить новую версию кода,
в обычном пользовательском PowerShell выполните
`.\scripts\start_commercial_qa_ui.ps1 -RestartOwnUi`.
Launcher остановит только процесс на `127.0.0.1:58097`, если Windows
подтвердит, что его командная строка запускает именно
`run_commercial_qa_ui.py`. При отказе в доступе или иной идентичности
процесса он остановится без завершения чужого приложения. Новый пароль
вводится интерактивно; старые сессии входа после перезапуска недействительны.
Этот параметр не запускает PostgreSQL или Docker.

`-EnableQaWrite` разрешает только локальную Stage 4 QA-базу после отдельного
операторского выбора режима в форме. Без `-StartLocalDatabases` launcher не
поднимает PostgreSQL. Он может открыть historical snapshot и без Stage 4;
QA write требует готовую Stage 4. Пароль запрашивается интерактивно и не
записывается в Git, отчёты или логи.

## Перед запуском

Нужны существующие локальные файлы:

- manifest: `reports\STAGE5D_2026-09-24\candidate_manifest_http_dry_run.json`;
- диагностический XML: `reports\STAGE5D_2026-09-25\final_qa\STAGE5D_COMMERCIAL_QA_POST_RECOVERY.xml`;
- пустой или новый каталог артефактов вне Git, например
  `reports\STAGE5D_2026-09-25\ui_runs`.

Не используйте порты 55447 и 55448 как веб-порт. Launcher сам не запускает
PostgreSQL: он лишь проверяет уже работающие разрешённые источники.

## Работа через браузер

Откройте `http://127.0.0.1:58097/`, войдите под именем `qa-operator` (или
заданным `-Username`) и паролем, введённым при запуске launcher. На странице
«Ручной сбор» выберите `Сохранённый Stage 5D manifest` для короткого
контрольного теста либо `Полный sitemap manifest трёх источников` для рабочего
охвата. Затем выберите поставщика, `Проверка без записи` или (только если
launcher запущен с `-EnableQaWrite`) `Сохранить в QA PostgreSQL`, ограниченную
партию либо `Весь подтверждённый manifest`, подтвердите QA-запись в форме и
нажмите «Запустить вручную».

Для ручного обновления всех трёх выберите `Обновить все три источника` в
полном режиме. Сайт производителя независим, но его данные справочные:
официальный JSON-LD без числовой цены не превращается в коммерческую цену.
Обычная кнопка запуска поставщика в read-only QA не используется: она
возвращает 403 и ссылку на этот отдельный безопасный маршрут.

Страница статуса показывает прогресс, PERSISTED и REVIEW отдельно. Локальный
`events.jsonl`, JSON-отчёт и sanitized evidence остаются только в заданном
каталоге артефактов. Прерванное задание после перезапуска не запускается
повторно. После успешной QA-записи диагностический XML пересоздаётся из
текущей QA PostgreSQL, затем пересчитываются диагностические предложения
matching и XML/XLSX/CSV по закреплённому GET-only Sterbrust snapshot.
Индекс файлов публикуется последним; при ошибке обновления статус `partial`
и прежний комплект остаётся доступен. Это не Sterbrust import payload и не
активация offer selection.
Форма показывает число кандидатов и нижнюю оценку времени по обязательной
паузе; фактическое время увеличивают страницы категорий и сеть. Карточки с
ошибками HTTP и REVIEW видны отдельно.

Для полного режима выберите `Полный каталог` и одного из трёх поставщиков
либо `Все три источника`. `Весь manifest` означает фактическое число
кандидатов, а не технический потолок 100. Discovery повторно проверяет SHA
перед карточками; изменение списка не продолжает старые offsets. Beka-Mak
TR остаётся справочным источником; его данные не становятся автоматически
ценой Sterbrust. Страница «Сопоставление и файлы» показывает только
диагностические предложения из отдельно созданного свежего QA snapshot,
не применённый matching/selection и не ESOL payload.

Остановка локального веб-процесса не должна останавливать PostgreSQL. Не
используйте эту инструкцию для ежедневного расписания или production
integration. При ошибке БД отчет сохраняет частичный результат, дальнейшие
GET прекращаются и автоповтора нет.

## Источники, отображаемые в единой панели

При запущенном `main_supplier_snapshot` на `127.0.0.1:55448` интерфейс
показывает исторические Partner-ST и Optimum как **«Восстановленный
исторический снимок»**. Это не LIVE-состояние и в него невозможно записать.

При отдельном штатном запуске Stage 4 на `127.0.0.1:55447` интерфейс также
показывает реальные коммерческие наблюдения Intervesp/Beka-Mak. Если один
источник недоступен, другой остаётся доступен, а отсутствующий помечается
«Источник не подключён», а не нулевым каталогом.

## Отображение Stage 4 QA после отдельного штатного запуска PostgreSQL

Если оператор уже штатно запустил исходный portable PostgreSQL и подтвердил
его идентичность, добавьте **до** команды launcher только:

```powershell
$env:COMMERCIAL_QA_DATA_SOURCE = 'stage4_readonly'
```

Это допускает только фиксированное подключение `127.0.0.1:55447`,
`stage4_commercial_qa`, `stage4_runtime`. Клиент задаёт
`default_transaction_read_only=on`; все POST-пути панели, кроме входа и
явного dry-run, блокируются. Partner-ST и Optimum не подменяются QA-данными:
без отдельного доступного источника интерфейс показывает «Источник не
подключён».
